# Repository conventions

This repository contains pyRevit tools for Autodesk Revit. Shared helpers, especially `lib/revitfunctions/PT_funcs.py`, support multiple commands and require careful changes.

## Scope and behaviour

- If the user requests a review or proposal without edits, keep the work read-only until edits are authorized. Once authorized, complete the requested change without repeatedly asking for permission.
- Keep changes focused. Preserve existing calculations, units, rounding, function signatures, parameter assignments, and transaction behaviour unless a change is explicitly requested or necessary to the agreed fix. Explain any intended behavioural differences.
- Before changing a shared helper, inspect its callers and references to any names being removed or changed. Avoid unrelated refactoring.
- Preserve existing file formatting and compatibility with the pyRevit engine used by the scripts. A local CPython check does not establish compatibility inside Revit.
- Keep `AGENTS.md` for repository-wide conventions and reusable lessons that apply across scripts. Whenever implementation, debugging, or user feedback reveals such a lesson, update the relevant section during the same task and keep it concise.
- A bug discovered in one function or script belongs in `AGENTS.md` when its cause or fix could help future code in another script. Record the reusable failure pattern, relevant API/runtime conditions, and corrective approach; a concise example from the originating script is appropriate. Do not require the bug to have occurred in multiple scripts before recording the lesson.
- Keep script-specific behaviour, thresholds, design decisions, limitations, and verification notes in [SCRIPTS.md](SCRIPTS.md), organised by script path where known. Read the relevant entry before editing a script and update it when its behaviour or verification status changes. In both files, distinguish observed results from assumptions or limitations.

## Revit document and view context

- Use one document context consistently for related calculations, queries, parameter updates, and element creation. Capture it when a command starts; make separate contexts explicit for deliberate operations across documents.
- Obtain views from that document using `DOC.ActiveView` or `doc.ActiveView`. When existing code uses `DOC`, keep its helpers tied to `DOC`; do not mix live `revit.doc` view data with creation against a different cached document.
- For new reusable helpers, pass the document or view explicitly. Avoid capturing active document or view objects in module globals that may survive across commands.
- Read level elevations and view ranges when needed, not during module import.

## UI previews

- For layout-only work, keep the existing command entry point unchanged and provide a separate preview launcher. A pyRevit pushbutton's `config.py` runs on Shift-click and can preview a WPF form without invoking its `script.py`. Disable model-changing and persistence controls until their behaviour is authorized; keep temporary reordering in memory and pass the document explicitly to material queries.
- When integrating a settings dialog with a command, capture the document and selection before opening it, return settings for execution only on an explicit Run action, and begin model transactions after the modal window closes. Close/X may remember settings but must not modify the model.
- For material-order presets, store names rather than document-specific element IDs and record the format version and priority direction. Reconcile against the current project: retain missing names in saved data and append new materials at the bottom. Validate imports before changing the displayed order, replace saved files only after a complete write, and use a pyRevit universal data file when preferences should survive sessions and Revit version changes.
- Highlight newly appended materials only when comparing against an existing remembered or imported order; first-time alphabetical initialization has no previous save to compare. For mixed-colour WPF status text, rebuild `TextBlock.Inlines` and apply a theme-specific warning brush to the notice's `Run`, keeping ordinary status text in its caption style and clearing old notices on subsequent updates.
- When removing XAML controls, remove their Python references and event handlers as well as unused layout rows, containers, and dedicated styles. Check remaining named-control references against the parsed XAML so a layout cleanup does not cause the window to fail during initialization.
- Keep compact dialogs free of headings that duplicate the window title. When adjusting WPF typography, check explicit font setters in text, button, caption, and tooltip styles; changing only the window's font size does not override those setters.
- Check the installed pyRevit implementation before using theme features from current online documentation. The installed WPF loader may lack `resolve_theme` and semantic brushes; for Revit 2024+, use `UIThemeManager.CurrentTheme` with local `DynamicResource` brushes when needed. Check control backgrounds, selection, hover, disabled states, and scrollbars in both light and dark layouts; Windows `SystemColors` alone does not follow Revit's selected theme.
- Keep button-state brushes separate from list and scrollbar hover brushes. Follow the chosen styling reference; different references can use opposite hover effects.
- Synchronous file writes in a WPF `Closing` handler delay the window disappearing. Save preferences only when dirty, including when project reconciliation changes them. For a reported close delay, measure the handler and file operations before attributing it to persistence; unchanged settings should bypass the write.
- If saving in `Closing` fails, cancel closing and clear any pending Run result so a later Close/X cannot execute a stale action. Keep edits available for retry/export, and allow an explicit discard-and-close path so an unwritable preferences file cannot trap the user in a modal dialog.
- For WPF multi-row reordering, snapshot selected names in list order and restore selection after collection moves. Preserve an existing selection on mouse-down until a click or drag is established; translate drag insertion gaps after removing selected rows. Account for scrolling and virtualized item containers, and leave the order unchanged when a drag is cancelled.
- RevitLookup's `develop` UI inspected in October 2026 uses [LookupEngine.UI](https://github.com/lookup-foundation/LookupEngine.UI), an adapted WPF UI library, with shared theme/control dictionaries and Revit theme-change tracking. Its custom XAML controls require compiled assemblies; inspect framework compatibility before importing them into pyRevit. When borrowing its appearance without that dependency, centralize the required brushes and standard-WPF templates in a reusable resource dictionary; note that its default dark button hover lightens rather than darkens.
- For loose-file WPF styles, load the root stylesheet from Python using an absolute file URI and use `DynamicResource` when styles are added after the window XAML loads. The installed IronPython loader did not resolve a window-relative dictionary `Source` in a standalone check; dictionaries loaded through an absolute `ResourceDictionary.Source` can resolve their nested relative files. Keep light/dark keys identical and merge the active palette after the shared styles. Verify resource loading with the installed loader, then check appearance in Revit.
- WPF brushes do not theme the native Windows title bar. Apply DWM caption settings after `SourceInitialized`, or immediately if pyRevit has already created the HWND. Declare HWND as pointer-sized and native BOOL/COLORREF/HRESULT values as 32-bit. On Windows 11, explicit caption/text colours follow the form palette independently of Windows' light/dark setting; log unsupported attributes or interop failures without preventing the form from opening.
- IronPython 2's `ctypes.byref(value)` can fail for a declared `c_void_p` argument with `expected pointer, got NativeArgument`; this occurred in Revit and was reproduced with the installed runtime. Pass `ctypes.c_void_p(ctypes.addressof(value))` and keep the value alive through the call. Test native marshalling with IronPython itself; CPython native-call tests and IronPython syntax/lifecycle checks alone missed this incompatibility.

## Bulk transactions and performance

- For new bulk-edit commands, prefer one overall `DB.Transaction` with a `DB.SubTransaction` per item or pair when immediate failures need independent rollback. Full transaction commits regenerate the document; committing separately for every item can be much slower. The improvement depends on the operation and model; preserve existing transaction behaviour unless changing it is authorized.
- A subtransaction isolates immediate exceptions and partial changes for its item, but its successful commit does not guarantee the overall transaction will succeed. Revit can detect additional failures at the overall commit. If that commit fails, the entire run is rolled back; report this accurately and do not retry items unless the user authorizes retries.
- In an `IFailuresPreprocessor`, distinguish `FailureSeverity.Warning` from errors. When warnings are authorized to be nonfatal, record their descriptions and failing element IDs before `DeleteWarning`; dismissing a warning does not repair the underlying geometry. Do not suppress unresolved errors or continue document access after a fatal regeneration failure. An independent post-commit verification failure can be reported without undoing other successful items when partial results are intended; exclude unverified work from success counts.
- When a failure offers an authorized native resolution, match its built-in failure ID and affected elements rather than translated message text. Check that the resolution exists and is permitted, scope it to the current operation, and guard against repeated attempts before returning `ProceedWithCommit`. For example, `ColumnInsideWallFailures.ColumnInsideWall` offers `DetachElements` (Unjoin Elements) in Revit 2026; verify the resulting join state after commit rather than only dismissing the warning.
- Scope commit-time resolutions to live successful change results rather than a snapshot of all candidate items. Otherwise a failed item can be modified during commit and omitted by success-only verification. Report every resolved item independently. Check existing known-invalid join warnings before editing; a relation/cutter check alone does not reject Revit's joined-but-disjoint warning, and an existing warning may not be reposted during commit.
- A `DB.TransactionGroup` combines Undo history; it does not eliminate regeneration from the full transactions inside it. When an operation requires verification after commit, a surrounding group can roll back the committed transaction if verification fails.

## Validation and error handling

- When serialized preferences store the same colour in multiple representations, update them consistently using the native colour conversion and preserve unrelated data. Validate the loaded appearance as well as the file structure.
- For gradient positions based on colour differences, normalise cumulative distances between adjacent colours in a perceptual space such as OKLab. Preserve the configured interpolation; changing stop positions does not create discrete colour bands or guarantee uniform perceived transitions within each segment.
- When matching configured labels and retrieved names, apply identical normalisation to both. For exact-name priority lists, build the rank lookup once per run and keep execution consistent with the displayed order.
- For geometry-based queries, report extraction or Boolean failures explicitly rather than treating them as zero overlap or a successful non-match.
- Add only checks required by the specific operation or needed for a useful error message. Level lookup checks for an associated level; view-range lookup checks for a plan view. Do not require unrelated view properties.
- For commands restricted to certain categories, filter selected elements before geometry/material caching and pair discovery. Enable execution using the eligible selection count, not the raw count, and report unsupported elements as ignored rather than failed operations.
- IronPython can ambiguously bind a Python integer to overloaded .NET constructors that accept both enums and numeric IDs. In Revit 2026, `DB.ElementId(1)` failed between the enum and `Int64` overloads during a read-only check; use `DB.ElementId(System.Int64(value))` for numeric IDs in Revit 2024+ and pass enum values explicitly when intended.
- For commands that already require an open Revit project, avoid redundant project-open guards.
- When adding logging, include useful context such as CSV row, operation, view, family, or parameter, along with the traceback. Keep rollback and stop/continue behaviour explicit; do not silently convert failures into success, skipped work, or fallback values.
- Keep successful runs quiet about log-file locations; display the saved log path once per run only when a warning or failure occurs.
- For partial family-based imports, resolve symbols once, warn once per missing family, and skip placement for that family while continuing available families. Preserve shared input context still needed by other categories.

## Verification and reporting

- Scale verification to the change. For shared calculation changes, compare representative outputs and side effects with the prior implementation, including relevant failure paths. Use focused mocks when Revit is unavailable.
- Review the final diff for unintended edits and run applicable syntax and whitespace checks.
- State what was actually verified and what still needs verification in Revit. Describe an unverified lifecycle scenario as conditional; do not present a mock reproduction as an observed Revit failure.
